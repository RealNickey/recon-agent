# Principal Staff Engineering Audit — `recon-agent`

Date: 2026-08-28  
Scope: current worktree, including the reconciliation engine, provider layer, API/dashboard, BenchRec ingestion, and evaluation scripts. Existing worktree changes were reviewed but not altered.

## Executive verdict

The repository is a credible buildathon demonstrator, not yet a safe close-grade financial reconciliation system. The deterministic matcher is fast and the current locked evaluation is excellent, but several production-shaped inputs can produce high-confidence false matches, and Tier 3 can commit an LLM assertion without independently recomputing the money relationship.

Observed validation results on this checkout:

- `bun run typecheck`: passed.
- `bun test`: 87 passed, 0 failed.
- `bun run loop-eval`: Dev 81/81, BenchRec subset 15/15, Holdout 66/66, Hard 62/62, all reported at fitness 1.0000 with zero false positives.
- `bun run cross-validate`: 10 generated populations, 100% mean/min/max fitness, with Tier 3 disabled in every run.

Those numbers are useful regression evidence. They do not prove independent generalization or financial safety because the cross-validation truth is generated by the same generator, the real BenchRec mix is a curated sample, and the AI path is not exercised by the advertised benchmark.

## 🔴 Critical flaws / immediate bugs

### R1 — Tier 3 trusts model confidence and candidate IDs without financial verification (P0)

Location: `src/pipeline/tier3-agentic.ts:190-226`, `src/types.ts:44-55`.

The model only needs to return a candidate ID and confidence at least `0.7`. The code filters IDs to the candidate pool, but never recomputes amount equality, subset sums, currency compatibility, FX rate, settlement window, sign, source legality, or whether all requested IDs were valid. The audit trail then labels the first candidate amount as “Verified” even when no verification occurred.

A mocked structured model response matched a bank record for `10 USD` to a ledger record for `999 USD` at confidence `1.0`; Tier 3 emitted reciprocal `matched` outcomes. This is a direct financial-integrity failure. Prompt instructions and Zod shape validation are not a control boundary.

Required fix: make Tier 3 proposal-only; independently validate every proposed group using fixed-point money arithmetic and explicit relationship rules before claiming it. Any invalid, incomplete, or unverifiable proposal must become an exception.

### R2 — Tier 2 has over-broad auto-match rules that create false positives (P0)

Locations: `src/pipeline/tier2-fuzzy.ts:206-242`, `:245-272`, `:368-410`; `src/normalize.ts:29-32`.

The same-invoice path accepts any amount ratio `>= 0.2` inside two days, including cross-currency pairs, without an FX-rate check. A `100 USD` ledger record and `20 EUR` bank record with the same reference auto-matched at confidence `0.96` and reason `currency_mismatch`.

`sameInvoice` considers any identical non-empty token an invoice identity, including generic values such as `WIRE` and `TRANSFER`; it does not require a numeric/strong token. The large-amount fallback then treats a single same-amount/date/currency pair as decisive solely because the amount is above the synthetic ceiling (`9001`). A `100000` bank record and unrelated `100000` ledger record auto-matched at confidence `0.94`. `amtDateCurKey` uses absolute amounts, so a large positive ledger entry and large negative bank entry with unrelated references also auto-match.

The FX rule is similarly not a currency/rate model: it allows any non-USD bank currency against any different ledger currency when the absolute amount ratio is in `[0.80, 1.25]`. INR/JPY or EUR/GBP can be accepted as if they were a supported corridor.

Required fix: use strong identity gates, explicit currency-pair allowlists, as-of FX rates and rate tolerances, sign/direction checks, and never promote a synthetic magnitude assumption into a production rule.

### R3 — The cascade can permanently commit an incomplete three-source group (P0)

Locations: `src/pipeline/tier1-exact.ts:41-91`, `src/pipeline/run.ts:82-84`.

Tier 1 commits any cross-source exact-key subgroup and removes it from the residual set. For a common payout shape—ledger gross `100`, processor capture `100`, bank net `97.64`—ledger and processor are committed as a complete match before the bank leg reaches Tier 2. The bank remains an exception and the full `{bank, ledger, processor}` truth group cannot be recovered.

The problem is not a concurrent race; it is premature graph contraction. A pairwise exact match is allowed to hide a better multi-leg settlement explanation.

Required fix: build candidate edges for all sources first and commit only globally valid groups. A settlement group should explicitly model gross, processor capture, fees/taxes, payout, refund, and chargeback legs.

### R4 — Input and coverage handling is fail-open for operationally important failures (P1)

Locations: `src/pipeline/run.ts:23-48`, `:76-112`.

Missing source files are silently treated as empty datasets. A nonexistent input directory therefore produces a successful zero-record run with zero exceptions and no warning. Malformed or duplicate rows are silently skipped and only an aggregate `skippedInvalid` count is retained; skipped records do not receive outcomes or reasons. Duplicate IDs are checked only within each source file, not globally. The declared `source` is not required to agree with the file being loaded.

The final invariant checks exactly one outcome per valid, accepted row, not every supplied row, and it validates neither `matchedIds` referential integrity nor reciprocal/group semantics. This is insufficient for an “honest exception list”: missing files and skipped financial rows can disappear from the close.

Required fix: fail closed on missing inputs, preserve row-level rejection records, enforce global ID uniqueness and file/source consistency, validate every claimed ID and group before serialization, and publish an input manifest.

### R5 — The advertised regression locks are not cryptographically enforced (P1)

Locations: `scripts/loop-eval.ts:25-34`, `:82-90`; `scripts/eval.ts:36-49`; `src/util.ts:61-95`.

The evaluator computes a truth hash but never compares it with the documented Dev/Holdout lock hashes. It trusts whichever external path the environment resolves to. The generator can also overwrite that external truth for the same dataset name. The holdout script’s historical comparison is against the previous log entry, not an immutable baseline.

The path containment check is case-sensitive on Windows; a case-variant path inside the repository was accepted by `pathIsInsideRepo`. It also does not resolve junctions/symlinks. Dataset classification relies on whether a path string contains `hard` or `holdout`.

Required fix: pin expected truth hashes and input-manifest hashes in code/configuration outside the matcher, canonicalize with `realpath` and case-insensitive comparison on Windows, reject mismatched dataset identities, and make generated truth unavailable to the benchmark runner.

### R6 — The local API exposes arbitrary filesystem reads/writes and the dashboard has DOM XSS (P1)

Locations: `src/index.ts:13-20`, `:42-74`; `public/index.html:802-812`, `:850-907`, `:976-987`.

`dataDir` is taken directly from query/body input and passed to `join` and `readFileSync`. `outFile` is also caller-controlled and is passed to `writeFileSync`. Any client able to reach the server can request records from arbitrary directories containing the fixed filenames or cause result writes outside the intended results directory. There is no authentication, authorization, path allowlist, rate limit, or request-size limit.

The vanilla dashboard concatenates record fields, model reasoning, trace data, and the chat prompt into `innerHTML` without escaping. A hostile description/reference or a chat message such as an image event-handler payload executes in the dashboard origin. That origin can then call the unrestricted API and exfiltrate records or overwrite results.

Required fix: anchor dataset/output paths to allowlisted roots, authenticate or bind the service to an explicitly trusted local boundary, validate request schemas, add rate limits and security headers, and use `textContent`/DOM node construction or a maintained sanitizer for every untrusted field.

### R7 — “No provider configured” still sends financial prompts to a third party (P1)

Location: `src/pipeline/agentic-providers.ts:82-85`; prompt construction in `src/pipeline/tier3-agentic.ts:103-136` and `src/pipeline/controller-agent.ts:22-42`.

When no API key is configured, the provider layer creates a dummy OpenRouter client rather than returning an offline/no-provider result. The next call still sends the full candidate payload, descriptions, references, and cash context to the external endpoint with `apiKey: "none"`. Even if the endpoint rejects it, data has crossed the local/provider boundary. With configured keys, fallback can route the same financial data through multiple unrelated providers, including free models, without redaction, consent, residency policy, or a budget guard.

Required fix: fail closed before network I/O when no approved provider is configured; make provider policy explicit, redact/minimize fields, and record provider/data-transfer consent and cost.

## 🟡 Architectural blind spots and missed edge cases

### Matching and claiming

- Tier 2 is greedy and order-dependent. Subset-sum claims consume records in input order; reversing the same records changed whether a distractor bank or the true bank consumed a shared ledger subset. Tier 3 has the same first-winner behavior when two model decisions select one candidate. There is no maximum-weight assignment, global ambiguity set, or deterministic tie report.
- Tier 1’s “zero false positives guaranteed” claim is too strong. A normalized reference/amount/date/currency collision is treated as one group with no identity-strength or collision analysis.
- Partial payment is a one-off pair rule, not an open-balance chain. Multiple receipts sharing an invoice are claimed one-to-one before one-to-many reconstruction; a `100` ledger invoice with `40` and `60` bank receipts produced one partial match and one residual.
- Refund/reversal logic only pairs same-sign negative records with shared identity. It does not model original-payment-to-refund chains, partial refunds, chargebacks, fee reversals, or net settlement events.
- Subset-sum is limited to at most 18 candidates and six members, with no indexed/meet-in-the-middle algorithm, cancellation, or workload budget. The surrounding scans are quadratic; repeated exponential searches can become a denial-of-service vector on large same-vendor windows.
- `amountAbsTol(target) = max(0.05, abs(target)*0.001)` has no monetary cap. At `1,000,000` the tolerance is `1,000`; at `1,000,000,000` it is `1,000,000`. This is not an acceptable generic reconciliation tolerance without a fee/FX rule and materiality policy.

### Normalization and money safety

- `RecordSchema` stores money as IEEE-754 `number`, so values above the safe integer range can already be rounded before `Decimal` sees them. It also accepts arbitrary precision, zero, and extremely large finite values.
- Currency is only non-empty; it is not trimmed, canonicalized, ISO-validated, or case-normalized. Dates pass a regex but invalid calendar dates such as `2026-02-31` are accepted and parsed as a different day.
- `vendorOverlap` divides by the smaller token set, so one shared token can produce `1.0` against a description containing many unrelated tokens. Reference token extraction can also treat generic numeric/year tokens or alpha-only references as identity.
- The generator and BenchRec adapter use `round2` with floating-point arithmetic. Because the truth is generated from the same rounded values, this can hide source-amount rounding defects in evaluation.

### Tier 3 and provider operations

- Raw descriptions, references, and prior model reasoning are interpolated into prompts without a strong untrusted-content boundary. A malicious transaction memo can instruct the model to select a candidate. Candidate-ID filtering limits arbitrary ID invention but does not prevent wrong in-pool claims.
- Model confidence is self-reported, not calibrated against deterministic evidence. Invalid mixed ID arrays are partially accepted rather than rejected atomically.
- Each fallback attempt gets a fresh 18-second timeout; there is no overall batch deadline. A batch can spend roughly the timeout across every configured model, while `calls` increments once per batch and cost accounting only reads OpenRouter metadata. Throughput, cost, and SLA reporting are therefore materially understated.
- `controller-agent.ts` hardcodes an insight saying the engine processed the run with “zero false positives” even though `RunResult` contains no false-positive metric. It also formats every currency with `$` and only the UI-selected USD/INR portfolio is displayed.

### Evaluation rigor and BenchRec

- Cross-validation does run 10 populations in its CLI default (five seeds × two modes), but every truth is created directly by `generateDataset` and scored immediately. It uses the same vendors, date span, amount ranges, category recipes, IDs, and synthetic assumptions as the matcher tuning history.
- Cross-validation bypasses `runPipeline` and never invokes Tier 3; every residual is converted directly into a Tier 2 exception. It does not enforce the orchestrator’s coverage checks and does not randomize input order, so it cannot substantiate the three-tier architecture or order robustness.
- BenchRec is genuinely sourced through the Kaggle adapter, but `fetch-benchrec.ts` samples only 20 reconstructable groups, intentionally discards non-reconstructable and duplicate/extra A rows, and uses the solution labels plus amount reconstruction to construct the in-repo sample. The reported 15/15 is therefore a curated, matcher-aligned subset, not full-dataset performance.
- BenchRec sampling uses a PRNG-backed non-transitive `sort(() => rng() - 0.5)` rather than a shuffle, has no pinned archive checksum/version, and appends fixed IDs to existing files. Re-running the fetch can duplicate IDs and truth entries.
- `scoreRun` implements the documented pair-level formula and union-find grouping correctly for normal well-formed pipeline output. It is not a complete verifier: `RunResultSchema` permits duplicate record IDs, arbitrary sources, unknown matched IDs, and inconsistent stats; the evaluator does not load the source records to validate those fields. Fitness is rounded before being returned, and category `honest` counts records while the other category counters count pairs.

### Finance-ops/product completeness

The engine closes a narrow “bank row ↔ ledger/processor group” loop and reports per-currency bank totals split by matched/unmatched status. It does not yet run the books or establish a close-grade cash position: there is no durable journal/adjustment proposal, account-level opening/closing balance, expected-vs-actual settlement ledger, fee/tax accrual, FX revaluation, refund/chargeback lifecycle, approval workflow, or exception ownership/SLA.

## 🟢 High-impact recommendations

1. **Replace greedy pair commits with a canonical reconciliation graph and global solver.** Normalize to fixed-point minor units; build all candidate edges first; solve one-to-one and grouped assignments with source, sign, time, currency, and amount constraints; defer contraction until the full settlement group is proven. Explicitly support gross sale → processor capture → fees/taxes → bank payout → refund/chargeback chains. Emit an ambiguity set when multiple solutions have materially similar scores.

2. **Make AI a constrained proposal layer behind a deterministic verifier.** Pass opaque candidate handles and minimized/redacted fields to approved providers. Recompute every amount/subset/FX/fee relationship locally; require exact source legality and complete group membership; reject unknown or mixed valid/invalid IDs atomically; ignore self-reported confidence unless calibrated against evidence. If no approved provider is available, return an honest exception without network traffic. Add adversarial prompt-injection fixtures and measure AI lift, false-positive rate, cost, and latency separately from deterministic tiers.

3. **Build a real close and evidence boundary.** Add an immutable input manifest, run ID, atomic result publication, row-level reject ledger, provider/data-transfer policy, and signed/exportable exception report. Pin BenchRec archive and truth/input hashes, keep the full external benchmark separate from tuning, randomize row order, evaluate the complete `runPipeline` including Tier 3, and add out-of-distribution cases for partial refunds, chargebacks, fee schedules, FX spreads, duplicated settlements, missing files, malformed rows, and large groups. Present cash by account and currency with explicit base-currency conversion rather than a dollar-formatted total.

## Recommended acceptance gates before claiming production readiness

- No matched outcome can reference an unknown ID, wrong source, invalid sign/currency relationship, or failed fixed-point sum.
- A missing/malformed source file produces a run-level failure or explicit row-level exception, never a successful empty input.
- Results are invariant under input permutation and deterministic under repeated runs; ambiguous assignments remain exceptions.
- Dev/Holdout lock hashes and input manifests are verified, not merely displayed.
- Tier 3 has an ablation report on the full benchmark, including provider attempts, cost, timeout rate, exact match precision, and false-positive count.
- The dashboard/API passes an authenticated/path-traversal/XSS test suite and never sends financial data to an unapproved provider.
